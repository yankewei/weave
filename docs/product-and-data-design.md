# Weave：第一版功能与数据设计

## 1. 设计状态

当前已实现账号与会话、工作空间隔离、项目创建和文档手工变更闭环，详见[实现说明](document-lifecycle.md)。管理员可以按邮箱邀请已注册用户、查看成员并移除成员；成员可以退出。邀请后的角色是成员，空间至少保留一名管理员。移除时会清空该成员负责的任务，并拒绝其待确认提案。内容权限仍只看当前是否为工作空间成员。每个账号可以保存一份 S3 兼容对象存储配置。工作空间可以另外保存一份，也可以用快捷方式使用某位管理员自己的配置；快捷方式不复制访问密钥。访问密钥使用 AES-256-GCM 加密后只留在数据库中，接口不会返回。任务看板支持手工创建、编辑、拖拽排序、筛选、变更历史以及评论与一级回复。项目对话可以调用模型生成创建任务的提案，发起人确认后走同一套任务写入和 `task_events` 记录，并带上提案标识。图片上传、文档提案、文档与任务关联和持久化队列仍未实现。任务历史与任务写入在同一事务提交。尚不能把成员提升为管理员。

技术栈、架构及下列变更追踪需求已确认；成员管理规则已实现。其余产品范围、权限规则和数据模型为待确认方案，不代表已经实现。

技术选型、界面方案和待定事项的完整汇总见[决策汇总与当前方案](decisions.md)。

### 已确认的技术决策

- 全栈：TypeScript + Next.js App Router，页面与 Route Handlers 在同一个应用内。
- 前端：React + TypeScript。
- 数据库：PostgreSQL。
- 架构：模块化单体，页面、Route Handlers 与服务层在同一个 Next.js 应用内运行。
- AI 修改流程：生成提案 → 用户确认 → 校验权限与版本 → 事务写入。
- 数据库访问采用 node-postgres 与 SQL 迁移；身份认证采用邮箱密码与数据库会话；AI 使用 AI SDK 与 Command Code。持久化任务队列尚未选定。

### 已确认的产品需求：每次变更可追踪

文档和任务每次发生正式变更，都必须保存可查询的历史，不能只保留最终内容，也不能只记录 AI 调用日志。

- 覆盖创建、内容修改、任务状态、负责人、优先级及文档与任务关联的变更。
- 手工编辑、AI 提案应用和文档历史恢复使用相同的追踪规则。
- 能查看何时修改、修改前后是什么、由谁发起、由谁确认，以及通过什么方式修改。
- AI 变更能追溯到触发消息、所在对话、AI 执行记录、提案及具体变更条目。
- 一次提案影响多个对象时，能从任一对象的历史找到本次操作及其他受影响对象。
- 文档和任务详情提供变更时间线与差异查看入口；这不是仅供管理员查看的系统日志。

## 2. 产品目标

做一个由 AI 驱动的简洁版 Jira + Confluence。用户通过对话澄清需求、生成文档、拆分任务和提出变更，也可以直接编辑正式内容。

对话用于讨论；文档和任务保存确认后的工作内容。AI 生成的内容在确认前不是正式需求。

## 3. 第一版范围（建议）

### 纳入范围

| 模块     | 功能                                                                                         |
| -------- | -------------------------------------------------------------------------------------------- |
| 工作空间 | 成员归属与团队数据隔离                                                                       |
| 项目     | 项目名称、说明，关联文档、任务与对话                                                         |
| 文档     | Markdown 正文、直接编辑、版本历史、恢复历史内容、变更时间线与差异查看                        |
| 任务     | 标题、描述、验收标准、状态、负责人、优先级、列表与看板、评论与一级回复、变更时间线与差异查看 |
| 对话     | 项目内讨论，可指定文档或任务作为上下文，流式显示 AI 输出                                     |
| 变更提案 | 预览文档与任务的新增或修改，确认或拒绝整份提案                                               |
| 执行记录 | AI 执行状态、失败原因及业务修改来源                                                          |

### 暂不纳入

- 多人实时协同编辑。
- 自定义字段、自定义工作流和插件系统。
- 任务依赖、子任务和迭代管理。
- 项目级独立成员与复杂角色配置。
- AI 自动执行正式修改、自动写代码或运行用户代码。
- 附件、外部工具同步和邮件通知。
- 向量检索和通用项目事实引擎。
- AI 删除正式文档或任务。

第一版不支持部分应用提案，避免同一需求只更新文档、不更新任务。

## 4. 权限与状态（建议）

### 权限边界

- 用户可以属于多个工作空间。
- 工作空间设置管理员和成员两种角色；创建者成为管理员。
- 管理员维护成员；管理员与成员均可管理工作空间内的项目内容。
- 项目继承工作空间成员范围，第一版不提供私有项目。
- 第一版只允许提案发起人确认或拒绝提案。
- 发起 AI 执行、读取上下文和应用提案时，分别检查当时的权限。
- 用户离开工作空间后，不能继续读取历史对话或确认旧提案。

### 固定状态

实现时使用枚举定义，不使用散落的字符串。

| 对象        | 建议取值                             |
| ----------- | ------------------------------------ |
| 任务状态    | 待办、进行中、完成                   |
| 任务优先级  | 低、普通、高                         |
| AI 执行状态 | 等待执行、执行中、成功、失败、已取消 |
| 提案状态    | 待确认、已应用、已拒绝、存在冲突     |

AI 执行成功只代表回答或提案已生成，不代表业务修改已应用。

## 5. 核心数据模型（建议）

以下是逻辑模型，字段类型、索引和数据库迁移在范围确认后细化。

| 表                      | 用途与关键字段                                                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `users`                 | 用户身份；具体登录凭据取决于认证方案                                                                                         |
| `workspaces`            | 团队数据边界：名称、创建者                                                                                                   |
| `workspace_members`     | 工作空间、用户、角色                                                                                                         |
| `projects`              | 工作空间、名称、说明、版本号                                                                                                 |
| `documents`             | 工作空间、项目、标题、当前 Markdown 正文、版本号、更新者                                                                     |
| `document_revisions`    | 文档、版本号、标题及正文快照、修改者、来源提案                                                                               |
| `tasks`                 | 工作空间、项目、标题、描述、验收标准、状态、负责人、优先级、版本号                                                           |
| `task_comments`         | 任务、父评论、作者、正文、创建时间；一级回复通过父评论关联                                                                   |
| `document_task_links`   | 工作空间、项目、文档、任务，记录任务对应的需求文档                                                                           |
| `conversations`         | 工作空间、项目、发起人、标题，可选的上下文对象引用                                                                           |
| `messages`              | 对话、发送者类型、用户、正文、所属 AI 执行记录                                                                               |
| `ai_runs`               | 工作空间、对话、触发消息、发起人、执行状态、模型信息、上下文来源与版本、错误、开始及结束时间                                 |
| `change_proposals`      | 工作空间、项目、AI 执行记录、发起人、状态、变更摘要、确认时间                                                                |
| `change_proposal_items` | 提案、操作类型、目标引用、目标基础版本、结构化修改内容                                                                       |
| `audit_events`          | 工作空间、项目、同次操作标识、目标及变更前后版本、操作类型、变更方式、发起人、确认人、修改前后内容、来源提案及条目、发生时间 |

### 关系

```text
用户 ←→ 工作空间成员 ←→ 工作空间
                           └─ 项目
                               ├─ 文档 ─ 文档版本
                               ├─ 任务
                               ├─ 文档与任务关联
                               └─ 对话 ─ 消息
                                          └─ AI 执行
                                              └─ 变更提案 ─ 变更条目

正式内容修改 ─ 操作记录
```

### 数据约束

- 成员关系在同一工作空间内唯一。
- 文档版本在同一文档内唯一；文档与任务关联不能重复。
- 正式对象之间的关联不能跨工作空间或项目；结合复合外键与业务校验约束。
- 任务负责人必须是所属工作空间的现有成员；成员退出时，其负责的任务改为未分配。
- 文档、任务、对话与提案查询均检查工作空间范围，不能只凭对象标识读取。
- 数据库生成的类型、前端类型和模型输出类型都不代替运行时输入校验。

### 文档与任务历史

- 文档保存当前内容，同时为每次正式修改新增不可变版本。
- 恢复旧文档是基于当前版本提交一次新修改，不回退版本号，也不删除后续历史。
- 任务第一版不单独建立版本快照表；版本号用于并发检查，修改前后内容保存在操作记录中。
- 不采用事件溯源，正式状态直接保存在业务表中。

### 变更记录与展示

- 每个实际发生正式变更的文档或任务都有对应记录，保存发生变化的字段及其前后值；创建时保存初始内容。
- 文档版本保存完整快照，操作记录关联对应版本，界面据此展示正文差异；任务字段的差异由操作记录提供。
- 关联关系变更记录关联对象，并更新受影响文档和任务的版本及历史，不能只写关联表而绕过追踪。
- 同一事务内的多对象修改共享同次操作标识；AI 修改额外关联提案及条目，以支持跨对象追溯。
- 发起人与确认人分别记录。手工修改二者均为操作用户；AI 修改标明由 AI 生成，不能把模型名称当作确认用户。
- 变更原因引用用户实际提供的说明或来源消息；AI 生成的摘要只能标为摘要，不能编造用户决策原因。手工修改不强制填写原因。
- 历史按对象版本排序，同时显示发生时间、人员、变更方式、差异和有权限访问的来源链接。来源读取也必须检查当前权限。
- 操作记录不可通过正常业务编辑或删除；恢复旧内容产生新的版本和记录，不覆盖原历史。
- 正式修改、版本和操作记录在同一数据库事务内保存。历史记录写入失败，业务修改必须回滚，不依赖异步日志补写。
- 未应用提案、执行失败和版本冲突保留各自执行或提案记录，但不伪装成对象已发生的正式变更。
- 重复确认已应用的提案不重复修改，也不追加重复变更记录；没有实际变化的编辑不增加对象版本。

## 6. AI 与正式写入边界

AI 可以读取有权限访问的上下文、请求澄清、生成回答、生成变更提案，不能执行任意 SQL，也不能自行确认提案。

提案条目是经过校验的结构化操作，不接受任意表名、字段路径或 SQL。第一版仅支持创建和修改文档、创建和修改任务，以及建立文档与任务关联。

正式内容修改只走一套业务逻辑，手工编辑、历史恢复和提案应用都不能绕过权限、版本检查、字段校验及操作记录。

### 同一提案内创建多个对象

例如“生成需求文档并拆成任务”，文档和任务尚无数据库标识。提案使用局部引用关联这些新对象，应用时在同一事务内转换成正式标识。

### 上下文与冲突

- 记录参与生成的正式对象及版本，便于追溯，不默认把全部项目内容交给模型。
- 对话和文档正文均作为不可信内容处理，不能改变工具权限或确认规则。
- 检查写入目标的基础版本，并检查作为关键需求依据的文档版本。
- 写入目标未变但需求依据已经变化时，也要求重新检查提案，不能视为安全修改。

## 7. 执行流程

### 生成回答或提案

1. 检查用户的工作空间和项目权限，保存用户消息与等待执行的 AI 记录。
2. 通过持久化任务机制交给后台进程，不只在接口进程内启动异步函数。
3. 后台进程重新检查权限，读取当前上下文并记录来源及版本。
4. 调用模型，将执行进度和输出传递给前端。
5. 校验结构化输出，保存回答或待确认提案；此时不修改正式文档与任务。

流式文本属于生成过程，不能当作已经通过校验的提案。生成失败时保留失败状态，不把不完整内容变为正式数据。

具体队列组件尚未选定，但必须解决执行记录保存后未成功入队的恢复、重复投递和工作进程崩溃后的重新执行。重试可重复调用模型，不能重复发布提案或产生业务副作用。

### 确认提案

1. 检查确认者是发起人，且当前仍有权限。
2. 开启事务，锁定提案记录，确认其仍待确认；重复确认已经应用的提案返回原结果。
3. 按固定顺序锁定相关正式记录，检查目标及关键依据版本，并校验字段和关联范围。
4. 创建或更新正式数据，写入文档版本和逐对象操作记录，关联同次操作标识、来源提案及条目。
5. 将提案标记为已应用，提交事务。

版本冲突时不写入任何业务修改，将提案转为存在冲突，展示冲突原因并由用户请求重新生成。数据库异常时回滚整次应用，不留下部分完成状态。

调用模型期间不持有数据库事务或行锁。模型输出的格式正确，不代表业务修改合法。

## 8. 实现前需要确认

1. 第一版范围是否接受，包括直接编辑、文档版本、列表和看板。
2. 是否接受工作空间统一权限，暂不支持私有项目。
3. 是否接受仅发起人确认、整份提案一次应用的规则。
4. 是否接受 Markdown 正文，暂不实现多人实时协同编辑。

基础工程与文档手工变更闭环已经建立。后续范围确认后继续细化队列、模型接入与提案契约。
