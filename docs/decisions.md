# Weave：决策汇总与当前方案

本文汇总项目讨论结果。已确认的决定、骨架已采用的组件与当前推荐方案分别记录，不能把候选组件当作已经选定的依赖。当前已实现登录、项目与文档手工变更、任务看板、任务评论与一级回复，以及通过对话生成并确认任务提案。工作空间支持邀请已注册成员、查看成员和移除；移除时解除任务负责人并拒绝其待确认提案，且至少保留一名管理员。文档正文支持上传图片：默认存到私有 Vercel Blob，管理员可以为工作空间改用自己的 S3 兼容存储，访问密钥使用 AES-256-GCM 加密；图片经服务端代理读取，只有成员可见。文档提案和持久化任务队列尚未实现。详见[文档闭环实现](document-lifecycle.md)。

## 1. 产品方向（已确认）

- 做一个由 AI 驱动的简洁版 Jira + Confluence，管理项目、文档与任务。
- 对话是主要操作入口：通过对话澄清需求、生成内容、拆分任务及提出修改。
- 保留内容阅读、列表、看板与直接编辑的界面方向，不要求所有操作都通过聊天完成。
- 区分讨论与正式结果，未确认的 AI 内容不能直接成为正式需求。
- 当前项目及仓库使用 Weave 名称；未核查商标、域名，也未确定中文品牌名称。

## 2. 技术与架构（已确认）

| 部分     | 决定                                              |
| -------- | ------------------------------------------------- |
| 语言     | 前后端使用 TypeScript，JavaScript 模块采用 ESM    |
| 后端     | Next.js Route Handlers + 服务层（`lib/services`） |
| 前端     | React 19 + Next.js App Router                     |
| 数据库   | PostgreSQL                                        |
| 应用架构 | 模块化单体，不先拆微服务                          |
| 运行方式 | 单个 Next.js 应用，页面、接口与数据访问同源       |
| AI 写入  | 生成提案 → 用户确认 → 校验权限与版本 → 事务写入   |

```text
Next.js App Router
    ├─ 页面 / 服务端组件 ─── PostgreSQL
    ├─ Route Handlers ─── 服务层（事务、权限、审计）
    └─ 模型调用（请求内流式返回）
```

AI 不直接执行任意 SQL，不自行批准修改。手工编辑与 AI 修改使用相同的业务校验和正式写入规则。

## 3. 每次变更可追踪（已确认）

这是业务功能，不只是后台日志。

- 文档与任务的每次正式变更都保留历史，包括内容、任务状态、负责人、优先级及关联关系的变化。
- 手工编辑、AI 提案应用与历史恢复都必须追踪。
- 记录变更时间、前后内容、发起人、确认人及修改方式。
- AI 修改关联来源对话、触发消息、AI 执行、提案与具体条目。
- 一次操作修改多个对象时，共享操作标识，可以查看同次操作影响的其他对象。
- 文档和任务详情提供历史时间线与差异查看，来源链接遵守当前访问权限。
- 业务修改、版本与历史记录在同一事务内保存；历史写入失败则整体回滚。
- 恢复历史内容产生新版本，不覆盖原记录；重复确认不重复执行或追加重复历史。
- AI 摘要与用户实际说明分开，不能编造变更原因。

## 4. 第一版功能（当前建议）

第一版围绕工作空间、项目、文档、任务、对话、变更提案与历史记录展开。

- 文档：阅读视图与所见即所得编辑、Markdown 存储、版本历史、恢复及差异查看。
- 任务：标题、描述、验收标准、状态、负责人、优先级、列表与看板、评论与一级回复。
- 对话：在同一项目内讨论，流式显示生成过程，生成待确认的任务提案。
- 提案：展示待创建任务，确认或拒绝整份提案；文档提案尚未实现。

建议暂不做多人实时编辑、自定义工作流、自定义字段、子任务、任务依赖、插件、附件、外部同步、AI 自动写代码、AI 删除正式对象和向量检索。

成员管理已经实现：

- 项目继承工作空间权限，第一版不做私有项目。内容是否可读可写只取决于当前是否为工作空间成员。
- 工作空间只有管理员与成员两种角色。邀请、成员列表和移除已实现：邀请后成为成员，管理员可以移除他人，成员只能退出自己，空间至少保留一名管理员。尚不能把成员提升为管理员。

已实现规则与尚待确认事项：

- 只有提案发起人能够确认或拒绝，暂不支持部分应用（已实现）。
- 第一版使用 Markdown，暂不做多人实时协同编辑。

## 5. 前端界面

### 布局

项目首页是工作台：这条对话占主要宽度，右侧列出本项目的进行中与待办，下方是工作空间概况（项目进度、最近文档、最近动态，由 `GET /api/workspaces/:id/overview` 一次返回）。没有消息时显示大输入框和可直接发送的起点卡片；有消息后记录在上、输入框在下，已确认写入看板的任务显示为产出卡片。没有项目时，第一句话会创建项目并开始这次对话。看板和文档仍是单独页面，可以从右侧打开同一条对话：面板宽度固定且不占满页面，缩小后变成始终悬浮的按钮。生成中的回复按流式显示。模型调用使用 Vercel AI SDK 的 `streamText` 和 `@ai-sdk/openai-compatible`，请求发往 Command Code 的 `deepseek/deepseek-v4.1-flash`，发生在 API 请求内，运行记录会先落库；进程中断后，超过 70 秒仍处于执行中的记录会在下次访问时标为失败。文档提案尚未实现，起点卡片只承诺拆出待确认任务。

```text
┌──────────┬──────────────────────────────────────┐
│ 项目导航 │ 问候与概况                             │
│          ├───────────────────────────┬──────────┤
│ 工作台   │ 对话记录 / 起点或这次产出 │ 进行中   │
│ 文档     │                           │          │
│ 看板     │ 输入框                    │ 待办     │
│          ├───────────────────────────┴──────────┤
│          │ 项目进度 · 最近文档 · 最近动态        │
└──────────┴──────────────────────────────────────┘
```

- 项目入口支持从对话开始，也能打开已有内容。
- 查看 AI 产出不离开当前对话；当前项目、文档或任务上下文应可见。
- 区分正在生成、等待确认、已应用、失败和冲突，不能把生成成功显示为修改已生效。
- 变更确认展示摘要、受影响对象和前后差异；冲突时禁止直接覆盖。
- 文档与任务详情具有历史入口，可以追溯来源对话和同次操作。
- 视觉采用 shadcn/ui Nova 中性主题，以内容和差异为主体；组件与交互约束见 `DESIGN.md` 和 `AGENTS.md`。
- 骨架在小屏幕上采用纵向堆叠；业务交互细节和完整视觉稿尚未设计。

| 本地数据库         | Docker Compose + PostgreSQL 17 配置已添加，应用已接入数据库并提供显式 SQL 迁移               |
| 生产部署           | 尚未定案                                                                                     |
| 包管理             | pnpm 11 单包；构建脚本许可写在 `pnpm-workspace.yaml`                                         |

TypeScript 使用 6.0 系列，以匹配当前类型检查与静态检查工具的兼容范围。具体版本由包清单和锁文件固定。

无论使用哪种队列，都必须支持任务持久化、失败恢复与重复执行保护。接口进程内的异步函数不能替代可靠任务队列。

## 7. 数据与执行约束（当前设计）

详细表结构与流程见[第一版功能与数据设计](product-and-data-design.md)。

- 核心数据包含用户、工作空间与成员、项目、文档及版本、任务、文档与任务关联、对话及消息、AI 执行、提案及条目、操作记录。
- 当前内容保存在业务表，不采用事件溯源。文档有完整版本快照，任务先通过版本号与操作记录提供追踪。
- 使用工作空间隔离数据，禁止跨工作空间或项目关联正式对象。
- 提案是受控的结构化操作，不接受任意表名、字段路径或 SQL。
- 同一提案中新建对象可以使用局部引用，应用时在事务内转换为正式标识。
- 应用前检查目标版本及关键需求依据版本，避免使用已经过期的需求修改内容。
- 模型执行期间不持有数据库事务或行锁。
- 未应用提案和失败执行不能显示成已发生的正式变更。
- 任务持久化与入队之间的失败、重复投递和后台进程崩溃都需要恢复机制。

## 8. 实施顺序（当前建议）

基础工程已建立，并完成文档手工变更闭环：注册登录、项目与文档创建、版本历史、差异与恢复。模型调用在请求内完成，尚未接入持久化队列。

先验证一条业务闭环：

> 提出文档修改 → AI 生成提案 → 查看差异 → 用户确认 → 正式修改 → 查看变更历史。

1. 确认剩余产品规则和基础组件。
2. 做文档、AI 对话、变更确认和历史页面原型。
3. 认证、数据库访问与迁移已接入；持久化队列仍待实现。
4. 文档手工变更闭环已完成；下一阶段接入 AI 提案，再扩展到任务生成、列表和看板。
5. 验证工作空间隔离、版本冲突、重复确认、事务回滚及任务恢复。
