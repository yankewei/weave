# 第 4 阶段 code review

范围：PHP 私有对话入口、接收凭据与 fencing 协调、历史读取、SSE 转发，以及 agent 的持久终态回写任务。nginx 的浏览器对话与提案路由继续使用 legacy，未导入真实数据或切换生产流量。

## 发现与修复

- P1：回执丢失后，同一 requestId 的修复可能被已经生成的 pending 提案挡住，导致输入长期停留 accepting。相同内容的既有接收凭据先于 busy/pending 检查处理；重试仍查重而不再次生成。测试在提案已经保存时重试丢失回执的请求。
- P1：PHP 准备输入后退出、agent 尚未接收时，只有新消息才能触发对账，刷新会一直显示 accepting。读取也会查询接收结果；15 秒接收窗口过后，仅当 agent 持久封存了该 admission 才关闭准备记录。agent 不可达时保留未知状态；封存后同一请求可重试，并开启新的接收窗口，不使用旧的“运行超过 70 秒就失败”逻辑。
- P1：已映射的 agent 记录丢失时，读取若再次调用创建接口，可能以空对话掩盖历史丢失。仅在 PostgreSQL 尚无映射时幂等创建；已有映射的缺失返回错误，不能静默重建。
- P1：旧请求封存后重试仍保留原 runId，若按初次执行时间选择最新执行，会显示后来已完成的另一轮。改按当前 admission 的时间选择，并在重试准备时更新执行开始时间；测试旧请求在另一轮结束后恢复为当前运行。
- P2：AMPHP 默认压缩会预读 text/event-stream。订阅明确使用 identity 编码，避开压缩缓冲，并保留 `X-Accel-Buffering: no`；测试检查编码及原始 SSE 帧。
- P2：鉴权复核若只在下一次 read 执行，慢消费者可能拖延撤权。独立定时复核登录会话和成员关系，失败关闭上游与对应连接；复核超时后的 Future 显式标记忽略，避免迟到异常成为未处理错误。

## 已复查的恢复和权限边界

- PostgreSQL 的准备与 agent 网络调用分开，网络或模型运行期间不持有项目/成员事务锁。相同请求标识的内容不一致返回 409；不同请求遇到已接收但未同步的执行不排队。
- 查不到回执不等于没接收：先调用 agent 的持久封存接口，再以 admissionId 条件更新 PostgreSQL；封存与迟到输入由 agent 串行协调。agent 返回已接受时修复原凭据，不能释放 busy 状态。
- 消息正文只进 agent SQLite，PostgreSQL 保存哈希、关联和状态。读取、分页和订阅都检查发起人及当前成员关系，上游 I/O 后再次鉴权，不把其他成员的旧共享对话当作自己的对话。
- SSE 采用拉取式 ReadableStream，不聚合消息、不建立 PHP 回放日志；下游断开、上游结束、撤权和响应丢弃均释放定时器与上游。撤权时关闭连接也能中断已阻塞的写；当前 nginx 至 PHP 使用 HTTP/1.1。
- 终态观察任务与输入准备一起持久提交，按 Pi Durable checkpoint 等待生成和重试回写；PHP 不可达、agent 重启后继续，不依赖页面轮询或进程内回调。HTTP 200 之外还必须收到明确的 acknowledged 回执，才能持久标记同步完成。
- 终态接口按 runId 幂等，只接受相同状态及模型的重试，不把终态改回 running。成员移除后仍允许写执行审计，但不能恢复成员身份、生成提案或应用任务。错误说明由 PHP 固定清理。

## 验证和结论

PHP 的真实进程测试使用临时 PostgreSQL schema 和可控 agent HTTP fixture，覆盖并发同 ID 提交、接收前失败、接收后回执丢失、agent 不可达、持久封存、刷新恢复、提案阻塞、映射丢失、分页权限、SSE 字节透传、断开取消，以及两个无人读取订阅上的成员撤销和会话过期。接收前后的 PHP 故障窗口通过持久状态与丢失回执模拟，未声称测试了 PHP 进程 SIGKILL。

agent 测试使用实际 Node 进程、临时 SQLite 和本地模型/业务 API，验证 PHP 回写失败后 SIGKILL、重启持久重试、已确认后再次重启不重复生成或投递，并继续覆盖第 2/3 阶段的恢复行为。不使用真实模型密钥。

修复后 PHP 52 项测试、agent 10 项测试通过。按上述范围复查无遗留阻断项，可进入第 5 阶段。兼容期仍保留项目级唯一约束，因此同项目不同所有者创建新私有对话要等第 5 阶段原子切换为 `(project_id, created_by)`；已有共享历史在导入完成前返回迁移未完成，不自动复制或共享。
